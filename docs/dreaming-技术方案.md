# Dreaming 技术方案

## 目标

Dreaming 在 daemon 管理的独立 Worker 进程中整理工作区会话，将值得复用的经验保存为长期记忆，并持续维护供后续任务使用的 Wiki、导航和注入上下文。后续任务既能快速获得少量核心信息，也能沿着来源按需读取记忆和会话证据。

Dreaming 同时整理 workspace 记忆和跨项目 `user` 记忆。工作区整理 Agent 按需提出跨项目候选，全局 Agent 串行比较现有 `user` 记忆并决定是否修改；两者均可不产生变更。全局处理复用 Dreaming 模型和开关，不要求用户审核或手动重试。用户明确要求保存、修改和删除记忆的能力继续保留。

## 记忆分层

```text
注入上下文：核心摘要、导航入口
        ↓ 按需读取
主题 Wiki：跨记忆的归纳、适用条件和主题关联
        ↓ 引用
长期记忆摘要：当前版本、历史版本及来源
        ↓ 引用
Session JSONL：原始对话、工具调用和结果
```

| 层次 | 内容 | 存储与职责 |
| --- | --- | --- |
| 会话事件 | 已持久化的对话及执行记录 | Session JSONL 是原始事实来源 |
| 记忆摘要 | 可跨 Session 复用的项目事实、决策、经验和教训 | 复用 SQLite `memories`，扩展版本及多来源关联 |
| Wiki 与导航 | 对摘要的主题组织和综合结论 | daemon 数据目录按 workspace 保存 Markdown 文件，可由摘要重新整理 |
| 注入上下文 | 从 Wiki 提取的核心摘要和导航入口 | daemon 数据目录按 workspace 保存 Markdown 文件，供主 Agent 的后续 Run 使用 |

Wiki 可以综合多条摘要形成结论，结论应关联支持它的摘要；摘要版本关联支持它的会话事件。引用能够逐层定位，引用存在仅说明来源可定位，不代表结论一定正确。已有记忆的 `sourceSessionId` 只有 Session 粒度，保留已有信息，不补造 Run 或事件来源。

Wiki 是有预算的导航和知识组织层。被移出 Wiki 的摘要仍保留并可通过现有混合检索找到。原始会话可用于进一步核对，工作区文件中的现状仍应以实际读取为准。

## 系统职责

- `packages/memory` 定义记忆版本、来源、Wiki 和整理所需的领域类型与操作，维护摘要和 Wiki 的关联规则；不直接读取 JSONL、SQL 或 HTTP。
- 主 daemon 继续负责现有会话事件、Session JSONL 追加、HTTP/SSE、主 Agent、记忆 API 和用户显式记忆操作，并管理 Dreaming Worker 的生命周期。
- 独立 Dreaming Worker 负责读取已持久化的 Session JSONL、提取摘要、整理长期记忆与索引、维护 Wiki、导航和待注入上下文，以及 Dreaming 的调度、模型调用和发布。Worker 使用独立 SQLite 连接，持久化实现仍属于 daemon。
- 模型凭据由主 daemon 统一管理，Worker 不独立写入凭据文件。进程间通信协调 Worker 生命周期、会话活动状态和凭据操作。
- `agent-runtime` 将 Worker 返回的核心摘要与导航装配到主 Agent 上下文，并提供按需读取的运行时入口；不直接实现 SQL 或文件读取。
- Web 复用现有设置体系，提供 Dreaming Provider 和模型配置，不新增 Wiki 浏览、审核或运行控制页面。
- Provider 和模型通过现有 pi-ai 模型与认证能力解析；Embedding 继续使用当前本地模型和现有混合检索。

Dreaming 不创建顶层会话，不将 Pi 原始事件暴露给 Web。后台提示词及协议标记放在所属模块的 `prompts` 目录，业务流程负责装配。

主 Agent 生成的会话事件继续由主 daemon 串行追加 JSONL，追加成功后再更新 Session 索引并发布 SSE。Worker 仅读取已持久化事件，不成为会话写入的必要条件。Dreaming 的模型调用和向量计算在 Worker 中执行；Worker 退出或 daemon 关闭时回收后台调用，恢复仍以 JSONL 和 SQLite 为准。

## 开关与模型配置

沿用现有 `generateMemories` 和 `useMemories` 设置：只有允许使用记忆且开启从对话中学习时，才安排新的 Dreaming 工作；关闭使用记忆时，主 Agent 不注入或读取记忆。显式记忆操作继续沿用现有规则。

Dreaming 使用独立的 Provider 和模型，配置入口复用模型设置。模型未配置、Provider 不可用或凭据缺失时，不启动分析，符合条件的 Run 保持待处理；模型调用开始后失败或超时，该 Run 记为失败，不重试。后台请求使用现有 daemon 凭据，不向 Web 返回凭据。

第一次生效时记录开启边界，不回溯历史 Run。每次重新开启建立新的开启区间；只有在同一开启区间内开始并结束的 Run 可参与分析，跨越开关边界的 Run 跳过。关闭开关后不启动新的分析批次，已经开始的批次继续完成，包括其后续整理和提交；重新开启不补处理关闭期间的 Run。

现有设置可能默认开启，升级时应建立明确的 Dreaming 生效起点，不能将旧的开启状态理解为历史 Run 均可处理。生效起点和后续开关变化需要持久化，保证 daemon 重启后仍按相同边界判断。

## 触发与调度

处理单位是已结束的顶层 Run。成功、失败和中止的 Run 都可分析；失败和中止的上下文必须保留原有状态，不能将未完成的尝试写成成功经验。每个 Run 只分析一次，处理成功、无候选或失败后都不会再次分析。

定时扫描 Session 没有活动 Run、最近会话活动已过去 30 分钟且符合开启边界的待处理 Run，将结果按开始顺序放入等待队列。队列按顺序取任务，执行前再次检查 Session 活动状态、空闲时间和记忆开关；不再符合条件时保持待处理，等待后续扫描。同一 Session 按 Run 顺序处理；不同 Session 可并发，分析并发上限为 2。同一 workspace 同时只有一个整理 Agent，每批最多接收 2 个 Run 的候选；整理过程中完成的候选进入后续批次。无候选的 Run 直接完成，不单独触发整理。

Run 结束、记忆开关变化以及分析或整理任务结束不触发立即扫描。已有等待队列在分析名额释放后继续消费；下一次定时检查在上次检查完成后等待固定间隔。Dreaming 执行期间拒绝修改或清除专用模型，以及会触发 Provider 配置刷新的操作，并向用户提示；已发生的异步配置变化在后续检查确认任务结束后刷新。

每次分析固定 Run 的已持久化事件范围。分析开始后用户继续使用 Session，不改变当前输入范围；新 Run 等待后续空闲条件。daemon 停止时取消运行中的后台调用；重启后尚未开始的 Run 继续等待调度，中断的分析及整理批次标记失败，不重新执行。

调度记录至少区分待分析、分析中、待整理、整理中、已完成、无候选和失败，并关联 workspace、Session、Run 与必要的时间信息。候选在进入整理队列前持久化；整理成功后清理本批候选。整理批次失败时不提交草案，本批候选不再重试，涉及的 Run 标记失败。候选状态及提交结果需要与 Run 状态一致，避免重启时重复处理。

## Run 分析

Worker 从 JSONL 读取该 Run 已持久化的文本事件，包括用户消息、Agent 完整消息、工具调用及结果，以及 Run 的终止状态。以 `sessionId`、`runId`、事件 `id` 和 `seq` 定位来源；读取和校验遵循现有 JSONL 恢复规则。

每个 Run 仅发起一次模型调用，输出结构化候选列表。候选包含摘要内容、适用条件、证据描述及一个或多个事件引用；可覆盖项目知识、用户信息和可能跨项目复用的经验。候选为空是正常结果。模型判断什么值得保留，不将候选类型变成必须覆盖的清单。

优先保留未来任务可能复用且不能简单从当前工作区规则重新读取的知识。不保存一次性进度、秘密或凭据，也不把没有依据的猜测表述为确定事实。失败结果作为失败证据保留，不推断未发生的成功。

模型输出使用 TypeBox 校验结构、长度和来源；来源必须属于本次分析的 workspace、Session、Run 和实际输入事件。会话内容和工具结果均为待分析数据，不作为改变 Dreaming 行为的指令。解析失败、校验失败、调用超时或上下文超限均记为该 Run 分析失败。

## 整理 Agent

整理 Agent 接收本批候选，结合现有摘要与来源决定如何更新记忆，并维护 Wiki、导航和注入上下文。Agent 使用独立 Dreaming 模型和专用工具，不访问通用 Shell 或直接修改工作区文件。

工具能力包括：

1. 搜索、读取当前 workspace 的长期记忆及版本和来源，复用现有关键词与向量混合检索。
2. 按引用读取当前 workspace 相关 Session 的文本事件。
3. 读取当前 Wiki、导航和注入上下文。
4. 在本批草案中创建或更新摘要、记录来源和关联、改写 Wiki、导航及注入上下文。

Agent 的写入工具只更新本批草案，不直接修改正式记录。没有记忆或 Wiki 变更时，直接完成本批 Run，不创建 Wiki 版本；有变更时程序校验目标 workspace、引用、字段与预算，只有 Agent 正常完成且全部校验通过后才统一提交。工具调用次数和运行时间设内部上限，达到上限按批次失败处理。

整理主题时，Agent 阅读相关主题并判断它们之间是否存在依赖、前置条件、排查路径等有实际意义的关系；有关系时使用 `[主题名称](主题文件.md)` 链接并简要说明关系，没有关系时不强制添加，也不强制反向链接。主题链接指向同一版本的 Wiki 文件，发布前校验目标存在。已发布的旧版本保持不变，后续整理时按实际内容维护关联。

### 记忆关系判断

| 判断 | 处理 |
| --- | --- |
| 重复 | 无新增来源时复用已有版本；新增来源时生成新版本 |
| 补充 | 生成新版本，补充条件、细节或证据，保留旧版本 |
| 条件不同 | 分别记录或明确版本、平台及适用范围 |
| 明确替代 | 生成当前有效的新版本，保留旧版本及来源 |
| 无法解释的冲突 | 保留双方及来源，在 Wiki 中说明冲突和不确定条件 |
| 证据不足 | 不将候选写成确定事实，可保留为待核实内容 |
| 无关 | 不修改已有摘要 |

没有再次出现的记忆不等于过期。Wiki 和核心摘要不把尚未解决的冲突写成无条件的确定结论。证据状态用于表达依据，例如用户明确说明、有实践依据、待核实、冲突或已替代；状态不代表已证明该记忆会改善任务。

## 存储与提交

在现有 SQLite 存储上通过显式 migration 增加必要数据：

- **摘要版本**：关联记忆 ID、revision、正文和适用条件等，保留旧版本；现有 `memories` 保存当前有效版本，继续服务现有接口和检索。
- **来源关联**：关联摘要版本与 Session、Run、事件 ID 或序号；一条摘要版本可有多个来源。历史数据可仅保留已有的 Session 级来源。
- **Wiki 发布指针**：按 workspace 保存当前 Markdown 目录的标识；Wiki、导航、注入上下文及其引用保存在按发布版本区分的 Markdown 目录中，旧版本保留。
- **调度和候选**：记录开启代次、Run 处理状态和分析候选；整理批次在运行时组合，不单独建表。

具体表名和字段由实现阶段按现有 repository 与 migration 约定确定。版本与来源需要支持引用当前及历史摘要，Wiki 默认引用当前有效版本；解释历史冲突时可以关联相关历史版本。已有手动记忆没有会话来源时保持原样。

Wiki 存放在 daemon 数据目录的 `dreaming/<workspaceId>/` 下。每次整理生成一个独立目录，包含主题 Markdown 文件、导航 `index.md` 和注入上下文 `context.md`；注入上下文从 Wiki 提取核心信息，通过导航关联主题，Wiki 文件通过稳定的摘要 ID 和版本关联记忆。目录不放进用户 workspace，避免后台整理修改项目文件。

整理阶段先在事务外完成模型调用、草案生成、校验和必要的索引准备，将完整 Markdown 写入新的批次目录；不得在模型调用期间持有 SQLite 写事务。文件写入成功后，在一个 SQLite 事务中更新摘要当前版本、历史版本、来源、Markdown 当前目录指针、批次和 Run 状态，并同步维护现有 FTS 与向量索引。新 Run 启动时在同一数据库读取事务中固定 Wiki 目录和可见记忆版本；Run 内按固定版本读取，因此提交前的新文件不可见；事务失败时旧目录仍生效，新目录作为未发布草案清理。事务成功后保留旧版本目录；daemon 重启时只清理从未发布的草案目录。这样 SQLite 和文件系统不需要跨系统事务，也能保证读取到的记忆与 Wiki 属于同一次提交。

索引继续作为可重建派生数据；本地 embedding 不可用时沿用现有关键词召回退化行为。

用户删除 Session 时沿用当前语义：保留记忆和 Wiki，移除指向该 Session 的来源关联，其他来源不受影响。记忆和 Wiki 不复制 JSONL 原文作为第二份会话事实源。

## 容量与读取

| 内容 | 第一版上限 |
| --- | ---: |
| 单个 workspace 的主题 Wiki 合计 | 40,000 字符 |
| 单个 workspace 的导航 | 4,000 字符 |
| 每次注入的核心摘要和导航 | 2,000 字符 |
| 底层记忆摘要 | 不受上述 Wiki 预算约束 |

整理 Agent 在预算内合并重复主题、压缩内容并选择需要保留的导航。最终草案超限则整批失败，不提交。预算按字符计算，不依赖具体模型的 tokenizer。

主 Agent 在每个 Run 启动时固定 Wiki 及可见记忆版本，并加载对应的核心摘要和导航；后台发布不改变正在运行的 Run。主 Agent 可通过专用只读工具按需检索记忆和读取 Wiki、摘要及会话来源。注入上下文和读取结果属于不可信派生上下文，不改变用户请求、工作区规则或工具权限。

完整导航与注入内容如何在两个预算间分配暂不细化；实现必须满足各自上限，并保留按需访问所需入口。

## 失败、停止与可观测性

- 无候选：Run 完成，不产生整理任务。
- 分析失败：Run 标记失败，后续 Run 继续，不重试。
- 整理失败、校验失败或提交失败：本批草案不生效，本批 Run 标记失败，不重试；其他批次继续。
- daemon 重启：未开始的工作继续等待；中断的分析和整理标记失败；已提交批次保持完成，未提交草案不生效。
- 关闭学习：已开始批次继续至成功或失败，不再启动新的批次。

后台任务使用有界超时和 `AbortSignal`，daemon 关闭时中止调用。内部日志记录 workspace、Session、Run、批次、阶段和安全错误码，不记录凭据、环境变量或会话正文。状态用于调度与排查，不要求用户参与处理。

## 实施步骤

1. **明确契约和数据迁移**：扩展记忆版本、来源关联、Wiki 当前内容、启用边界及工作状态；保留现有记忆与索引兼容性。
2. **贯通最小链路**：为单个符合条件的 Run 读取 JSONL 文本，一次调用提取候选；整理 Agent 基于候选生成记忆和 Wiki 草案，成功后原子提交。
3. **接入调度和生命周期**：实现 30 分钟空闲判定、每 Session 顺序、最多两个 Run 并发、每批最多两个 Run、workspace 串行整理，以及失败和重启处理。
4. **接入主 Agent 与设置**：配置独立 Provider 和模型；移除自动 `learn_memory` 职责；注入当前摘要和导航，提供逐层读取工具，保留现有混合检索。
5. **验证并同步架构文档**：检查持久化、来源追溯、边界、读取和失败语义，更新 `docs/架构设计.md` 与运行配置文档，使其反映最终实现。

## 验证与效果评估

开发过程中使用已有会话和隔离数据验证：

- 运行结束状态、开启区间和 30 分钟空闲条件是否正确；关闭、重新开启和重启后是否符合处理边界。
- 成功、无候选、失败和超长输入是否分别产生正确状态；整理失败和中断是否保持整批不生效。
- 摘要版本、多个来源、Session 删除后的关联，以及 Wiki 到摘要再到事件的逐层读取是否正确。
- 重复、补充、替代和冲突处理是否保留适用条件与证据；Wiki 和注入预算是否生效。
- 现有检索和明确保存、修改、删除记忆的能力是否保持可用；关闭记忆使用后不注入或读取记忆。

链路完成后选择少量代表性真实任务，对照不使用长期记忆、使用 Dreaming 整理前的记忆、使用整理后的记忆三种情况。各组保持请求、模型和可用环境一致；无记忆组仍保留 `AGENTS.md` 和工作区文件，但不注入或搜索长期记忆。涉及文件修改或命令执行的对照使用隔离副本。

观察任务结果、过期记忆的使用、重复排查、模型调用和耗时。少量真实任务用于发现具体问题，不作为长期效果的充分证明。

## 第一版暂不处理

- Wiki、导航和运行状态的浏览、审核、手动重试或控制页面。
- 单个超长 Run 的分段处理；上下文超限按失败处理。
- 图片、PDF 页面等非文本内容的分析。
- Dreaming 与用户同时修改记忆的专门协调流程；现有用户修改能力保留。
- 失败任务的自动或手动重试；超时和工具调用次数使用内部上限。
- 历史 Wiki 和记忆版本的清理策略。
- 完整导航与注入上下文之间的具体内容分配策略。
