# 全局记忆与用户个性设计

## 范围

长期跨项目信息拆分为两类独立业务：

1. **用户个性（User Profile）**：用户的背景信息、沟通习惯、专业能力、兴趣、一般偏好和做事方式。使用独立 SQLite 表 `user_profiles` 存储，**只能通过用户在 Web UI 手动输入、更新和删除**，不参与 Dreaming 整理，也不进入 `global_memory_versions`；Run 启动时拍进快照全量注入上下文。
2. **全局记忆（Global Memory）**：仅记录具备明确适用条件的跨项目通用经验与知识，使用 `memories` 表的 `scope = 'global'` 承载（不再包含 `profileFacet`）。用户可在 Web UI 查看、创建、修改和删除全局记忆；工作区 Dreaming 也可提出跨项目候选，由全局整理 Agent 整理写入。项目事实继续保存在所属工作区，Web UI 不查看或修改工作区记忆。

## 候选与整理

每个工作区同时只运行一个整理 Agent，按 Session 和启动时间依次处理该工作区的全部符合条件的 Run。Agent 判断这些材料是否包含有长期复用价值的跨项目内容，没有时不产生候选。候选保留内容、适用条件、依据和可追溯的会话事件引用。工作区整理成功后候选进入全局队列，整理失败时不进入队列。

队列保存在 Dreaming Worker 内存中，由一个全局整理 Agent 串行分批消费。不同工作区可以并发整理，不等待其他工作区；整理运行期间新产生的候选留给后续批次。全局整理复用现有 Dreaming 模型、凭据、取消、超时和上下文压缩机制，并仅受 `generateMemories` 开关控制（不受 `useMemories` 耦合）；关闭 `generateMemories` 不中止正在运行的全局整理批次，只阻止启动下一批。

全局整理 Agent 将候选与当前跨项目全局记忆比较，判断重复、补充、适用条件不同、替代、冲突和证据不足。它可以拒绝任意候选，也可以保持现有全局记忆不变；没有值得复用的经验时不提交。冲突或修正时更新已有记忆而不是重复创建。未解决的冲突保留条件和来源，不写成无条件结论。草案只在 Agent 正常完成且通过校验后提交；无实际变化时不创建新版本。

## 并发控制与版本复用

跨项目全局记忆维护发布版本 `global_memory_versions` 和不可变副本。用户创建、修改或删除全局记忆，以及全局整理产生实际变化时，都发布新版本并保存对应副本。单条记忆同时保留自身 `revision`、版本内容、来源与向量副本；用户修改也必须保存修改前后的版本内容和向量副本。

**双向并发修改策略：**

- **后台整理期间用户修改全局记忆（乐观锁 + 增量合并）**：全局整理开始读取快照时记录 `baseVersion`；准备写入时再次比较最新版本号。若版本一致则原子提交；若版本已变化（此时只可能来自用户在 Web UI 的修改），则计算 `baseVersion → latestVersion` 期间的精确结构化变更（新增、修改、删除），将工具视图切换到最新版本，由当前全局 Agent 将新版本内容与已起草草案做**增量合并**。合并遵循**用户修改权威更高、冲突以用户为准、用户新增避免语义重复、用户删除不得复活**的原则，支持覆盖或撤销已有草案；合并完成后再以最新版本号走乐观锁原子提交（设有限合并轮次，持续撞车时放回队列稍后处理）。
- **用户在编辑界面停留过久，期间后台先提交（单条版本冲突 + 手动刷新）**：用户在 Web UI 保存或删除时携带 `expectedRevision`。若后台仅修改了其他条目则直接保存成功；若后台刚好更新了同一条记忆，后端返回 `MEMORY_CONFLICT` 错误提示“内容已更新，请刷新”。前端**保留用户当前表单输入不自动覆盖**，展示冲突提示并提供手动「刷新」按钮，由用户决定是否先复制已编辑内容再手动拉取最新数据。

顶层 Run 启动时在 `RunMemorySnapshot` 中固定开关状态、用户个性副本、全局记忆版本和工作区版本，直接加载用户个性与完整的跨项目全局记忆；运行期间的发布或开关切换不改变该 Run 的读取结果。关闭 `useMemories` 时不注入或检索任何记忆；关闭 `generateMemories` 时不启动新的记忆写入工具或自动整理。

## 失败与恢复

Worker 退出或重启后，内存中尚未完成的全局候选丢失。模型失败、超时或中止不发布草案，本批候选不再重试。删除来源 Session 时按现有语义移除来源关联，不删除已保存的记忆。
