# PI Harness 的 Dreaming 实现

> 2026-11-22 说明：本文记录改造前的“分析 + 整理”两段式设计。当前实现已合并为一个带工具的 Dreaming Agent：初始只给 Run 元数据，事件、记忆和 Wiki 按需分页读取，并复用 `projectContext` 上下文压缩。最新设计见 [Dreaming 技术方案](../docs/dreaming-技术方案.md)。

项目的初始方案里有个例子。一次联调中，设置 `FOO=1` 后，旧版配置的集成测试跑通了。过了几轮，又有一次测试没显式设置这个变量也通过了。下一次遇到测试失败，Agent 应该沿用哪次经验？

这得先看两次跑的是什么测试、配置版本有没有变化，以及工具结果能证明什么。记一句「测试需要 `FOO=1`」当然省事，到了另一个版本却可能让排查多绕一圈。把两轮对话原样塞给模型，排查成本又回到了下一轮。PI Harness 做 Dreaming，是想把值得复用的经验提前整理好，同时给后来使用这条经验的人留一条核对的路。这里的测试场景来自设计文档，用来说明取舍。[Dreaming 初始方案](../docs/dreaming-初始方案.md)

## 趁会话空闲，把判断留给后台

前台 Agent 正在帮用户定位故障时，优先要把故障排清楚。它在中途看到的线索可能只维持了几分钟，接下来的工具结果就会推翻它。项目原先有一个让主 Agent 主动学习的入口。Dreaming 把自动学习移到后台，等这一轮已有结局，再看哪一段经历值得留给以后。用户明确说「记住这个偏好」时，仍走当下的显式保存入口。

调度同时看两个条件。**Run 结束决定材料完整，会话空闲决定什么时候开始读。** 同一个会话里，用户可能紧接着追问一次；如果每轮结束就发起后台模型调用，前台仍在推进的问题会持续触发分析。现有实现以 Session 最后一条持久化事件为准，等至少 30 分钟并确认没有活动 Run，再调度已结束的 Run。Worker 通常在每轮扫描结束后等 60 秒再查，出队时会复查空闲状态。分析一旦开始，输入范围便固定下来，用户随后发出的消息交给以后的 Run。

Web 提供「使用记忆」「从对话中学习」和「Dreaming 模型」三个设置入口。两个开关默认开启，专用模型默认留空。一个 Run 要在同一次开启期间开始并结束才有分析资格。用户在一轮中间关掉学习再打开，哪怕开始和结束时开关都亮着，这轮仍会被跳过。Daemon 用 SQLite 中的开启代次识别这种情况，结束事件写进 Session JSONL 后才登记为待分析。后来启用功能也不会回扫此前没登记的会话。

分析任务由 daemon 管理的独立 Worker 执行。主进程继续追加会话日志、服务前台 Agent，子进程用自己的 SQLite 连接读取进度、调用模型和发布记忆。它通过 IPC 向主进程确认会话是否活跃，并复用 daemon 的模型凭据管理。前台请求因此无需等待后台分析与向量计算。不同 Session 最多并行分析两个，同一 Session 一次只处理一个 Run。

## 先找出发生过什么，再决定以后记什么

回到测试的例子。单 Run 分析只负责从这一轮里提取有依据的候选。它看到的是选定 Run 的完整消息、工具调用与结果、终态等已持久化事件。成功、失败和主动中止都可能提供材料。一条合理的候选可以写成「在这次使用的旧版测试配置下，设置环境变量后集成测试通过」，再附上相关事件。候选保存适用条件和证据说明，因此第二次测试通过时，两份材料还能放在一起判断。

这一阶段用一次模型调用返回结构化 JSON，不运行工具循环。程序用 TypeBox 校验输出，并从本次输入事件里查找模型给出的每一个事件 ID。它会补齐真实事件序号，遇到不在输入里的事件 ID 就拒绝整份结果。一个可以定位的引用说明「能回去看」，结论是否真的得到支持，还要看当时的条件。候选为空是正常结束。

有候选才进入工作区整理。同一个工作区一次由一个整理 Agent 处理，最多合并两个 Run 的候选，不同工作区可以并行。整理 Agent 可以检索现有记忆，回看候选引到的事件。旧结论碰上新材料，可能只是多了一份证据，也可能需要缩小适用范围。测试类型和配置版本还没对上时，就保留差异和不确定性。项目用同一个记忆 ID 下的不同 revision 保存这些变化，增加一个此前没有的真实来源也会生成新版本，旧版本及其来源仍能查到。

工作区 Agent 发现有些内容能跨项目复用时，可以再提名。例如，用户明确说出的长期偏好可以进入 `user` 作用域，有适用条件的通用排查经验也可以提名。这个环境变量在某版测试配置中的用途则属于当前工作区。**跨项目复用需要单独判断。** 工作区整理成功后，提名才会进入 Worker 的内存队列，由全局 Agent 串行处理，每批最多 20 条。它会拿现有全局记忆与候选比较，可以合并证据、补充条件，也可以整批不改。可复用的技术经验可以作为全局记忆，只有个人信息类记录会用于派生用户画像。

## 记忆写下来以后，下一轮怎么用

工作区的做法是给 Agent 一页短摘要，想查细节时再往下读。每个顶层 Run 启动时加载当前工作区 Wiki 的 `context.md`，通过 `index.md` 找到主题页。主题页可以归纳多条记忆，并引用具体 revision。Agent 怀疑测试条件变了，就能按引用查原记录，再回到 Session JSONL 看工具输出。它也可以直接搜索记忆，检索结合关键词与本地向量排名，向量不可用时仍可用关键词查找。全局记忆当前会完整注入，并携带适用条件和必要的证据状态。

```text
工作区核心摘要 → Wiki 导航 → 主题页 → 记忆版本 → 会话事件
全局记忆正文 → 记忆版本 → 会话事件
```

这里有一个用户能感受到的一致性问题。Agent 读完摘要开始排查，后台刚好更新了主题页。如果这时继续沿旧摘要打开新 Wiki，引用就可能对不上。PI Harness 在 Run 启动时用一次 SQLite 读事务固定全局发布副本、工作区 Wiki 目录和可见记忆版本。该 Run 的上下文与按需读取使用同一份快照，后续 Run 才跟进新发布。

写入端也围绕这件事设计。整理 Agent 只有专用的记忆和 Wiki 工具，提交的修改先留在内存草案。服务确认 Agent 正常结束，再检查文件预算、导航链接和记忆引用，把完整 Wiki 写到 daemon 数据目录的新版本下。最后在一次 SQLite 事务内核对旧指针和记忆 revision，再一起更新记忆、来源、索引、Wiki 指针及 Run 状态。读端认数据库里的发布指针，目录写到一半时读者仍看旧版本。模型调用也在事务外完成。整批没有实际改动时，只完成任务，不生成新 Wiki 版本。

全局发布也有版本检查。比如用户刚手动改了自己的偏好，全局 Agent 手里还拿着改动前的副本。提交发现全局发布版本已变，就把本批候选放回队列，下一次按新版本重新比较。工作区发布遇到 revision 或 Wiki 指针冲突会放弃本批草案，旧发布内容继续可用。

## 哪些情况等一等，哪些情况到此为止

| 情况 | 当前处理 |
| --- | --- |
| 会话重新活跃，或专用模型尚未配置、暂时不可用 | 未开始分析的 Run 保持待处理，等以后满足条件再扫描。 |
| 用户关闭「从对话中学习」 | 暂停新分析和新一批全局整理。已开始的任务可以继续，已经持久化候选的工作区整理也可以继续启动。 |
| 模型看完没有找到值得保存的内容 | 空候选正常结束。整理发现全是重复内容时，也可以正常结束且不发布新版本。 |
| 模型超时、分析结果解析失败或引用越界 | 已认领的分析记为失败，当前实现不自动重试。单 Run 分析的超时是 120 秒。 |
| 整理超时、工具调用超限、Wiki 校验或提交失败 | 未发布草案作废。工作区整批 Run 标记失败并清空候选，新目录会清理。全局模型调用失败、超时或中止会舍弃本批，提交时发现全局版本冲突才重新排队。 |
| 本地向量生成失败 | 记忆仍可随关键词索引发布，向量交给已有索引重建流程。 |
| daemon 关闭或 Worker 异常退出 | 关闭时取消后台工作，异常退出后由主进程重启 Worker。已登记但未开始的工作可以接着等，已经进入分析或整理的工作记为失败。启动时会用 JSONL 的终态补齐等待记录，并清理未发布目录。尚未处理的全局候选保存在内存，进程退出时会消失。 |

这张表体现了持久化上的取舍。工作区候选和 Run 进度一起落入 SQLite，重启后还能接着整理。跨项目提名目前只保存在内存，恢复能力到已发布的全局记忆为止。两个整理 Agent 都有 300 秒的超时和 40 次工具调用上限，超限会中止草案处理。[Dreaming 技术方案](../docs/dreaming-技术方案.md) · [全局记忆设计](../docs/全局记忆设计.md)

## Dreaming 能管到哪里

它处理的是已经持久化、符合开启条件的顶层 Run，产物是供下一轮参考的记忆。工作区规则和实际环境仍由项目文件和当前工具结果说明。回到测试例子，Agent 可以利用旧经验先检查测试配置；遇到新版文档和当次结果支持不同做法时，就按当前证据判断。Dreaming 可以保留失败教训、补充来源、修订结论，源事件的存在本身无法保证模型推断正确。自动整理无需逐条审批，用户仍能显式保存和修改记忆，对话工具发起的删除继续走审批。

后台整理 Agent 能操作记忆和 Wiki 草案，工具范围没有项目 Shell 或工作区文件写入权限。会话和工具结果按数据交给模型，历史记录里的文字也不授予权限。如果选的是远程 Provider，投影后的会话和工具文本会随分析请求发给它。投影会移除图片，文本仍可能包含敏感材料。

来源能追溯到哪里，还取决于原始记录是否保留。删掉来源 Session 后，已有记忆保留，对应的来源关联会移除。删除工作区记忆还会级联删除其 revision 和来源，旧 Wiki 里的引用可能失效，后续整理需要修正这些引用。工作区摘要、主题和导航都有字符预算，简短的常驻上下文容纳不了的内容，可以通过搜索和查证补回来。要衡量 Dreaming 的效果，还得回到后续任务，看 Agent 有没有少做重复排查，有没有因为旧经验走错方向。
