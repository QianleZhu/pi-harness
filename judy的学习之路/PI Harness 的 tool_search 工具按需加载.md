# PI Harness 的 tool_search 是怎样按需加载工具的

Agent 接入的 MCP 服务越来越多时，工具列表也会跟着变长。每次请求都把所有工具的描述和参数结构交给模型，会占用上下文，也会让模型面对大量与当前任务无关的选项。

PI Harness 给模型提供了一个 `tool_search` 工具。模型需要外部能力时，可以先描述自己想做什么，搜索匹配的 MCP 工具。选中的工具会进入下一次模型请求，模型随后就能看到完整参数结构并调用它们。

这篇文章结合项目代码，沿着一次工具搜索说明整个过程。代码位置主要在 `packages/tools` 和 `packages/agent-runtime`，本地向量模型由 daemon 装配。

## 从一个 Issue 查询开始

假设用户希望 Agent 查找某个 GitHub 仓库中与 SSE 重连有关的 Issue。已接入的 MCP 服务提供搜索 Issue、查看 Issue 和创建 Issue 等工具。下面的名称和搜索结果仅用于说明，实际模型调用名由 daemon 生成，排序也取决于服务提供的工具资料。

Run 开始时，daemon 已经从本地能力目录准备好 MCP 工具定义，但这些定义默认不在模型可见的工具列表中。模型可以看到基础工具，其中包括 `tool_search`。需要查询 Issue 时，模型可能发起这样的调用。

```json
{
  "query": "搜索仓库中的 Issue",
  "limit": 2
}
```

`query` 描述所需能力，`limit` 控制本次最多加载多少个工具。默认值为 8，允许的范围是 1 到 10。整个 Run 最多向模型暴露 64 个工具，这个数字也包括已经可见的基础工具。

Runtime 首先筛选当前 Run 中尚未公开的 MCP 工具，再搜索它们的资料。如果已经没有可见工具名额，搜索会报错。候选工具随本轮准备的目录固定下来；在本轮之后刷新出的新目录，需要等下一轮 Run 才会参与搜索。

## 搜索时看的是哪些资料

每个 MCP 工具都会有自己的定义。搜索时，项目从中提取工具标签、工具描述，以及参数 schema 里的名称和描述。参数提取会继续遍历嵌套的对象、数组和组合 schema。

一个虚构的 Issue 搜索工具可能提供下面这些资料。

```text
GitHub / search_issues
Search issues in a repository
repository  Repository name
query       Search query
```

工具标签通常带有服务名和上游工具名。参数信息也参与搜索，所以即使工具描述里没有写 `repository`，只要参数名或参数描述里有它，词面搜索仍有机会匹配到。

完整 schema 保存在 Registry 中。搜索阶段会使用提取出的文字进行匹配，工具被选中后，完整 schema 才会出现在后续模型请求里。对于向量化，项目将标签、描述和参数文字组合成一段文本，其中描述和参数文字各截取前 900 个字符。BM25 则使用完整的描述和提取出的参数文字。

## BM25 怎样找关键词

BM25 是一种给文档和查询计算关键词相关度的排序算法。在这里，每个工具的资料相当于一篇文档。工具资料与查询的关键词越吻合，通常越可能排在前面。

分词由项目自己的 `searchTerms` 完成。它先拆分 camelCase，把下划线、斜杠和连字符转成空格，再转换成小写。接着提取文字和数字片段，并处理中文与英文。

连续中文超过两个字时，代码会按相邻双字切分。比如“搜索仓库”会得到 `搜索`、`索仓`、`仓库`。这是简单切片，并不判断每个片段是不是一个有意义的词。英文则做有限的复数归一化，例如 `issues` 会变成 `issue`，`queries` 会变成 `query`。查询中重复的词会去重，工具资料里的重复词会用于统计词频。

假设查询被拆成 `github`、`搜索` 和 `issue`，三张示例工具卡片的词项如下。

| 工具 | 词项 |
| --- | --- |
| A，搜索 Issue | `github`、`搜索`、`issue`、`仓库` |
| B，创建 Issue | `github`、`创建`、`issue`、`仓库` |
| C，查找代码 | `github`、`查找`、`代码`、`仓库` |

BM25 会统计每个查询词在各张卡片中出现的次数，也会统计多少张卡片包含这个词。`github` 出现在所有卡片里，区分能力比较弱；`搜索` 只出现在 A 中，因而更能帮助找到 A。

### BM25 的计分公式

项目对查询中的每个不同词项分别计分，再把这些分数相加。对于查询 Q 和工具资料 D，公式如下。

```text
score(D, Q) = Σ IDF(t) × [ f(t, D) × (k1 + 1) ]
                         / [ f(t, D) + k1 × (1 - b + b × |D| / avgdl) ]

IDF(t) = ln(1 + (N - df(t) + 0.5) / (df(t) + 0.5))
```

求和符号 `Σ` 表示遍历查询中去重后的每个词项 `t`。符号含义和项目的取值如下。

| 符号 | 含义 |
| --- | --- |
| `N` | 本次可搜索的候选工具总数 |
| `df(t)` | 资料中包含词项 `t` 的候选工具数量，每个工具最多计一次 |
| `f(t, D)` | 词项 `t` 在当前工具资料 D 中出现的次数 |
| `|D|` | 当前工具资料拆出的词项总数，重复出现的词也计入长度 |
| `avgdl` | 本次所有候选工具资料的平均词项数 |
| `k1` | 词频饱和参数，项目使用 `1.2` |
| `b` | 长度归一化参数，项目使用 `0.75` |
| `ln` | 自然对数，代码使用等价的 `Math.log1p` 计算 IDF |

查询词如果没有出现在某个工具的资料中，也就是 `f(t, D) = 0`，代码会直接跳过这个词，它对该工具的贡献为零。查询词本身先去重，所以同一个词在查询中重复多次不会重复加分。

### 每项分数代表什么

IDF 衡量词在当前候选集合中的区分能力。包含某个词的工具越少，该词的 IDF 通常越高。在前面的例子中，`搜索` 只出现在 A 的资料里，能更明确地指向 A。`github` 出现在三张卡片中，能够区分工具的程度就低一些。即使一个词出现在所有工具中，项目使用的 IDF 公式仍会给它一个大于零的值。

词频部分衡量一个词在当前工具资料中出现了多少次。出现次数增加通常会增加分数，但增长会逐渐变慢。以资料长度恰好等于平均长度为例，`k1 = 1.2` 时，词频为 1 的倍率是 1，词频为 2 时约为 1.375，词频为 3 时约为 1.571。词频继续增加，倍率会趋近 `k1 + 1`，也就是 2.2。

长度部分通过 `|D| / avgdl` 调整词频的贡献。其他条件相同时，工具资料比平均长度长，分母会变大，得分降低；资料较短时，得分会相应提高。`b` 控制这种调整的程度，`b = 0` 表示不按长度调整，项目使用的 0.75 会让长度参与计分。

### 把示例分数算出来

沿用上面的三张卡片，假设表格中的词项已经完成归一化和拆分。候选工具数 `N = 3`，三张卡片的长度都是 4，所以 `avgdl = 4`。三个查询词的文档频率和 IDF 分别如下，数值保留三位小数。

```text
搜索  df = 1   IDF = ln(1 + (3 - 1 + 0.5) / (1 + 0.5)) ≈ 0.981
issue df = 2   IDF = ln(1 + (3 - 2 + 0.5) / (2 + 0.5)) ≈ 0.470
github df = 3  IDF = ln(1 + (3 - 3 + 0.5) / (3 + 0.5)) ≈ 0.134
```

每个匹配词都只出现一次，且每张卡片的长度都等于平均长度。将 `f = 1`、`|D| / avgdl = 1` 和 `k1 = 1.2` 代入，词频与长度部分的倍率恰好为 1。

```text
1 × (1.2 + 1) / (1 + 1.2 × (1 - 0.75 + 0.75 × 1)) = 1
```

因此每个匹配词的贡献等于它的 IDF，三张卡片的总分如下。

```text
A = github + 搜索 + issue = 0.134 + 0.981 + 0.470 ≈ 1.585
B = github + issue        = 0.134 + 0.470         ≈ 0.604
C = github                ≈ 0.134
```

这里是为了便于理解而构造的词项和分数，实际搜索会根据工具标签、描述和参数提取结果重新统计。候选集合发生变化时，`N`、`df` 和 `avgdl` 都可能变化，同一工具的分数也会随之变化。

### 项目怎样使用分数

词面检索保留精确名称命中或 BM25 分数大于零的工具。排序时先看是否精确命中，再按 BM25 分数从高到低排列；两项都相同时按工具名排序。除了大于零这一筛选条件，代码没有设定固定的 BM25 高分或低分等级，也没有把分数转换成百分比。

这些分数适合比较同一次查询中的候选，不适合直接解释成“匹配概率”，也不应拿不同查询的原始分数直接比较。没有精确命中且向量检索可用时，项目会用两路排名进行 RRF 融合，后续排序依赖名次而不是直接相加 BM25 分数和向量相似度。

查询如果与模型工具名或上游原始工具名归一化后完全一致，项目会将它视为精确命中，优先返回，并跳过这次向量计算。普通词面索引使用上游名称，模型别名中用于区分服务器的哈希不会作为普通关键词参与索引。

## 本地向量模型怎样参与搜索

BM25 能找到词面相同的内容。遇到中文查询和英文描述时，两段话即使表达的意思接近，也可能没有相同关键词。项目用本地向量模型补充这类搜索。

Daemon 创建 `LocalMemoryEmbedder` 后，把同一个实例交给长期记忆服务和 `AgentManager`。工具搜索通过 `HybridToolSearch` 使用它。模型是固定 revision 的 `Xenova/multilingual-e5-small`，通过 `@huggingface/transformers` 的 feature extraction pipeline 在 CPU 上运行，使用 q8 精度。

模型在第一次需要向量时才加载。项目会检查 `globalRoot/models` 下的缓存文件；文件齐全时从本地加载，否则使用模型 ID 和固定 revision 初始化，并使用该目录缓存模型。模型不可用时，工具搜索仍可以退回 BM25。

向量化时，查询和工具资料会加上不同的前缀，符合该模型的输入格式。

```text
query: 搜索仓库中的 Issue
passage: GitHub / search_issues. Search issues in a repository. Parameters: ...
```

模型将每段文字转换为 384 维向量。代码使用 mean pooling 和归一化，每批最多处理 32 段文本，并检查返回向量的数量、维度和数值。

查询向量会在每次搜索时计算。工具资料的向量保存在进程内缓存中，缓存键包含来源、工具名和向量化文本，资料发生变化后会使用新的键。缓存最多保存 4000 个工具向量，daemon 重启后会重新生成。

## 向量怎样比较

向量是一串数字。项目将查询向量与每个候选工具向量逐项相乘，再把结果相加，得到点积。由于输出向量已经归一化，这里的点积等价于余弦相似度。

可以把它想成比较两段话在语义空间中的方向。相似度越高，模型认为它们越接近。这个判断依赖模型，并不能保证每次都准确。

假设某次查询的最高相似度是 0.88，项目会保留与最高分相差不超过 0.05 的语义候选，最多保留 60 个。这个条件是相对最高分的范围，并没有设置固定的最低相关度门槛。如果候选工具整体都不相关，仍可能有工具进入语义候选。

向量生成失败、返回无效结果或超过 18 秒时，搜索会回退到 BM25。调用方主动取消时，取消错误会继续向上传递。

## 两份排名怎样合并

BM25 分数和向量相似度的数值含义不同，项目使用 RRF，也就是倒数排名融合，按照两份结果里的名次计算分数。

```text
单路分数 = 1 / (60 + 名次)
融合分数 = BM25 的单路分数 + 向量检索的单路分数
```

假设搜索 Issue 的工具在两份名单中都排第一，它会得到两份 `1 / 61` 的分数；只在 BM25 名单中排第三的工具则得到 `1 / 63`。融合结果按分数排序，最多返回 10 个候选。

Runtime 会再次检查 Run 是否仍然有效，并根据请求的 `limit` 和剩余可见工具名额截取结果。向量搜索期间如果有工具已经被加载，Runtime 也会再次过滤，避免重复占用名额。

## 加载之后发生了什么

选中工具后，Runtime 检查工具名是否属于本轮 MCP 目录，确认数量没有超限，然后把名称加入 Run 的 `visibleToolNames` 集合，再用这个集合更新 `agent.state.tools`。

`tool_search` 的返回结果只包含工具名称、标签、来源和简短描述。Agent 准备下一轮请求时，`prepareNextTurnWithContext` 会把新工具加入请求的 `context.tools`，完整 schema 在这个时候交给模型。已加载的工具在当前 Run 后续请求中保持可见。worker 子 Agent 使用自己的可见工具集合，和主 Agent 分别维护加载状态。

搜索和加载不会授予工具执行权限。模型真正调用 MCP 工具时，仍要经过参数校验、Policy 判断、必要的审批以及配置和定义复查。实际执行时才建立或复用对应的 MCP 连接。

工具进入实际模型请求时，Runtime 会记录工具加载事件。会话 JSONL 因此能够帮助 Trace 还原每次请求实际看到了哪些工具。
